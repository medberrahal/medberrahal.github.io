# Lab Recov : récupération de données supprimées et analyse mémoire sous Linux

> **Cible :** `176.16.132.37` (NixV2 for Recov)
> **Système :** Ubuntu 18.04.3 LTS, noyau `5.4.0-1071-aws`
> **Objectif :** récupérer deux flags via récupération disque et analyse mémoire, sans exécuter les binaires suspects
> **Résultat :** ✅ 2 flags récupérés par analyse statique + forensique disque et mémoire


## 1. Objet du rapport

Ce rapport documente la résolution du lab **Recov**, consacré à la réponse à incident, à l'analyse de fichiers, à la récupération de données supprimées sous Linux et à l'analyse mémoire. L'objectif était d'identifier deux flags en partant d'une machine compromise fournie par le lab.

> ⚠️ **Périmètre de l'analyse :** les manipulations décrites ont été réalisées uniquement sur la machine d'entraînement `176.16.132.37`, avec le compte fourni par le lab. Les exécutables `/opt/disk` et `/opt/mem` ont été analysés comme des artefacts suspects. **Ils n'ont pas été lancés manuellement pendant l'analyse.**

**Pourquoi cette étape est-elle nécessaire ?**

`uname -a` établit le contexte système et peut révéler une architecture 64 bits, une version de noyau et un environnement cloud. `id` indique l'utilisateur courant et ses groupes. Le test `sudo -n` vérifie uniquement si sudo peut être utilisé sans interaction ; il n'essaie pas de deviner un mot de passe. Dans ce cas, sudo exigeait le mot de passe fourni par le lab.

> 💡 Cette distinction est importante en DFIR : la capacité à lire `/proc/<PID>/mem`, une partition brute ou des journaux protégés dépend souvent des privilèges disponibles.

## 5. Recherche de dumps et d'images mémoire

```bash
find / -xdev -type f \
  \( -iname '*.raw' -o -iname '*.mem' -o -iname '*.lime' \
     -o -iname '*.dmp' -o -iname '*.vmem' -o -iname '*dump*' \) \
  -printf '%s %p\n' 2>/dev/null | sort -n
```

Cette recherche n'a pas révélé de dump mémoire autonome appartenant au scénario. Les résultats concernaient principalement des fichiers système, des pages de manuel et des fichiers de documentation.

**Pourquoi cette étape est-elle nécessaire ?**

Dans une investigation réelle, un dump peut être présent sous une extension connue, mais il peut aussi être caché, renommé ou uniquement maintenu en mémoire par un processus actif. L'absence de fichier `.raw`, `.mem` ou `.dmp` ne signifie donc pas qu'il n'existe aucune preuve mémoire. Il faut ensuite examiner les processus actifs et leurs mappings mémoire.

## 6. Énumération des processus actifs

```bash
ps auxwwf
```

Un processus s'est immédiatement distingué :

```text
root      1532  99.9  0.0   4388   804 ?  R  15:31  9:48 /opt/mem
```

Dans une collecte ultérieure, le même processus apparaissait ainsi :

```text
root      1532     1  14:24 R  100  0.0 /opt/mem
```

**Interprétation :** le processus `/opt/mem` était lancé par `root`, avec le PID `1532`, et consommait environ 100 % d'un cœur CPU. Son nom et son comportement correspondaient directement à la partie « memory analysis » du lab.

La consommation CPU élevée suggérait une boucle active. Le désassemblage a ensuite confirmé que le programme attendait l'apparition d'un fichier, le lisait, puis entrait dans une boucle infinie.

**Pourquoi cette étape est-elle nécessaire ?**

Un processus actif peut conserver en mémoire des données qui ne sont plus présentes sur le disque. Cette situation est classique lorsqu'un programme lit un fichier puis le supprime. L'analyse des processus permet donc de préserver une preuve volatile avant qu'elle ne disparaisse.

## 8. Compréhension de la logique de /opt/disk

```bash
objdump -d -M intel /opt/disk \
  | sed -n '/<make_file_name>/,/^$/p; \
           /<read_flag>/,/^$/p; \
           /<check_for_flags>/,/^$/p; \
           /<main>/,/^$/p'
```

> ⚠️ Une première tentative avait utilisé une option `objdump` incorrecte :
> ```text
> objdump: option '--disassemble' doesn't allow an argument
> ```
> La commande a été corrigée en désassemblant tout le fichier puis en filtrant les fonctions avec `sed`.

### 8.1 Fonction check_for_flags

Le code de `/opt/disk` montrait que `check_for_flags` vérifiait l'existence de la chaîne située à `0x2004`. La section `.rodata` révélait cette chaîne :

```text
/home/local.txt
```

La fonction retourne 1 si ce chemin existe et 0 dans le cas contraire.

### 8.2 Fonction read_flag

La fonction `read_flag` ouvre `/home/local.txt`, puis lit `0xfa` octets, soit 250 octets, dans un buffer global nommé `flag` situé à l'adresse symbolique `0x40c0` :

```asm
mov edx,0xfa
lea rsi,[rip+0x2e6f]        # 40c0 <flag>
call read@plt
```

Cela signifie que le contenu du fichier est copié dans la variable globale `flag`.

### 8.3 Fonction main

La fonction principale effectue les opérations suivantes :

1. Elle attend que `/home/local.txt` existe.
2. Elle efface le buffer global `flag` avec `memset`.
3. Elle lit le contenu de `/home/local.txt`.
4. Elle supprime `/home/local.txt` avec `unlink`.
5. Elle appelle `make_file_name`.
6. Elle crée temporairement un chemin dérivé du contenu du flag.
7. Elle attend deux secondes, supprime ce chemin et libère la mémoire.

### 8.4 Fonction make_file_name

Cette fonction alloue un buffer, écrit `/home/` au début, puis ajoute le contenu de `flag` à partir de l'offset 6. Le résultat est donc un nom de fichier de la forme :

```text
/home/<contenu_du_flag>
```

Le binaire supprime ensuite ce fichier. Le flag n'était donc pas nécessairement présent comme un fichier permanent ; il pouvait exister dans le nom d'un fichier temporaire ou dans un bloc de la partition après suppression.

## 9. Compréhension de la logique de /opt/mem

```bash
objdump -d -M intel /opt/mem \
  | sed -n '/<check_for_flags>/,/^$/p; \
           /<read_flag>/,/^$/p; \
           /<main>/,/^$/p'
```

La logique était analogue, mais le comportement final était différent.

La fonction `read_flag` lit 250 octets dans un buffer global situé à `0x40a0` :

```asm
mov edx,0xfa
lea rsi,[rip+0x2e9f]        # 40a0 <flag>
call read@plt
```

Après la lecture, `main` copie les 256 octets du buffer global vers une zone située sur la pile, puis boucle sur l'instruction :

```asm
jmp 12b5 <main+0x99>
```

Le processus conservait donc le contenu du flag **en mémoire**, même après la suppression du fichier source.

## 10. Tentative de récupération par debugfs

La partition racine a d'abord été identifiée avec :

```bash
findmnt -no SOURCE,FSTYPE,OPTIONS /
```

```text
/dev/nvme0n1p1 ext4 rw,relatime,discard
```

Recherche des inodes supprimés :

```bash
echo infected | sudo -S debugfs -R 'lsdel' /dev/nvme0n1p1
```

```text
Inode  Owner  Mode    Size      Blocks   Time deleted
0 deleted inodes found.
```

**Interprétation :** la commande `lsdel` n'a trouvé aucun inode supprimé exploitable. La partition était montée avec l'option `discard`, ce qui peut entraîner la libération rapide des blocs supprimés. Dans ce contexte, la récupération classique par inode supprimé pouvait échouer, même si des fragments du contenu existaient encore ailleurs sur la partition.

**Pourquoi ne pas s'arrêter à cet échec ?**

En DFIR, l'échec d'une méthode ne prouve pas l'absence de la donnée. Il faut changer de source de preuve. Ici, deux possibilités restaient ouvertes :

- le contenu pouvait subsister dans les blocs bruts de la partition ;
- le contenu pouvait être présent dans la mémoire du processus `/opt/mem`.

## 11. Récupération du flag mémoire

Le processus `/opt/mem` étant un exécutable ELF de type **PIE**, l'adresse symbolique `0x40a0` n'était pas directement utilisable comme adresse virtuelle finale. Il fallait d'abord obtenir la base de chargement ASLR depuis `/proc/1532/maps`.

```bash
PID=$(pgrep -f '^/opt/mem$' | head -1)
echo infected | sudo -S cat /proc/$PID/maps | grep '/opt/mem'
```
